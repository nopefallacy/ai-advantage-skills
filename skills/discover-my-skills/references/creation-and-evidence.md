# Creating the selected skills

Read after the person chooses the grouping and any material uncertainty is resolved.

## Keep the deliverable small and usable

Each generated skill needs a folder with a `SKILL.md` containing YAML `name` and `description`, followed by task-specific instructions. The description should identify when the skill is useful. The instructions should express the established outcome, required inputs, workflow, preferences, and criteria for a good result.

Put substantial situation-specific rules, templates, and accepted examples in supporting reference files when useful. Link each file from the entrypoint and say when it should be read. Keep common instructions in one place within a skill. Do not create documentation just to fill a predetermined folder structure.

For one combined skill, make it clear how to select the appropriate workflow. For separate skills, make each usable without inaccessible shared paths. Preserve relevant explicitly requested existing skills when available; if a required skill is unavailable, explain the missing dependency and clarify how to proceed. Do not pretend to have read or reproduced it.

Use the current environment's file-creation capabilities to deliver downloadable or local files. If files cannot be created, provide clearly labeled file contents and state that they have not been installed. Do not claim that a text shortcut alone installs or activates a skill. Verify platform-specific installation guidance before giving it.

## Preserve evidence without cluttering the working instructions

Provide a compact evidence note alongside the generated skill package, covering:

- **Coverage:** which sessions or supplied sources were inspected, and material gaps.
- **Requirement and scope:** what the user explicitly requested, and where it applies.
- **Source:** an actual conversation title with a retrievable link, date, message locator, or supplied-file location, using only identifiers available in the source.
- **Status:** explicit instruction, supplied final example, explicitly accepted result, newly clarified requirement, or accepted process improvement.

Use short excerpts only where they clarify the rule. Do not copy entire private conversations into the package. Never invent links or label a last draft as accepted without supporting evidence. If a reference cannot be reopened elsewhere, say so and include the minimal relevant excerpt that the person needs to review the finding.

Example of a concise finding, using hypothetical evidence:

> **Client update writing:** preserve the direct opening and plain-language explanations requested in the revision exchanges. Keep the client-specific formatting in a reference file. Sources: the inspected update conversations, with their actual locators.

This example illustrates presentation only; it supplies no default writing preferences for real users.

## Review before delivery

Check that each instruction is supported by inspected evidence, a direct answer, or an accepted improvement. Check that source-specific rules have not become universal, declined changes are absent, references resolve, and the user's chosen grouping is preserved.

If there is a suitable historical task, use its original request and inputs to try the generated skill, then compare the output with the user's explicit corrections and any accepted result. Call this a retrospective check, not independent proof. If execution or evaluation is unavailable, report that limit. Do not imply that packaging validation proves output quality.

Finish with the files, a brief explanation of what each skill handles, and any unresolved limitation affecting use. Installation, public sharing, or changes to other skills require the relevant user request; do not perform them merely because files were generated.
